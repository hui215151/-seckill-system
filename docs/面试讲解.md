# 面试讲解手册

> 用法：先看「30 秒版」和「2 分钟演示」，再把「高频追问」过一遍。
> 所有数字都来自本机实测（见 `benchmark/README.md`），不要背成生产指标。

---

## 一、30 秒自我介绍版

> 这是我做的一个高并发秒杀练习项目，技术栈是 Spring Boot + Redis + RabbitMQ + MySQL。
> 核心解决三件事：用 Redis Lua 原子预扣 + MySQL 乐观锁防超卖；用 RabbitMQ 异步建单，避免请求把数据库打垮；用本地事务表 + 重试/死信队列 + 对账任务处理消息可靠性。
> 我在本机做了压测：200 并发大约 340 TPS；500 库存、4000 多个请求下，最终订单正好 500、库存 0，没有超卖。
> 我也清楚它的边界：单机、JWT 没有刷新机制、活动信息还是一次 DB 查询，这些在生产化时要改。

## 二、2 分钟演示脚本

前置：应用和依赖已启动（MySQL 3307 / Redis 6379 / RabbitMQ 5672）。

```bash
# 1. 商品列表（公开接口，12 个商品，含未开始/已结束）
curl http://localhost:8080/api/seckill/goods

# 2. 登录拿 token
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"123456"}'
# 返回 {"token":"eyJ...","userId":1,"username":"alice","expiresIn":7200}

# 3. 不带 token 下单 → 401（证明鉴权生效）
curl -i -X POST "http://localhost:8080/api/seckill/do?goodsId=1"

# 4. 带 token 下单 → 200，返回临时订单（异步落库）
curl -X POST "http://localhost:8080/api/seckill/do?goodsId=1" \
  -H "Authorization: Bearer <token>"

# 5. 查结果 → 能看到订单
curl "http://localhost:8080/api/seckill/result?goodsId=1" \
  -H "Authorization: Bearer <token>"

# 6. 同一用户再抢 → 请勿重复秒杀
curl -X POST "http://localhost:8080/api/seckill/do?goodsId=1" \
  -H "Authorization: Bearer <token>"

# 7. 未开始 / 已结束
curl -X POST "http://localhost:8080/api/seckill/do?goodsId=11" -H "Authorization: Bearer <token>"  # 活动未开始
curl -X POST "http://localhost:8080/api/seckill/do?goodsId=12" -H "Authorization: Bearer <token>"  # 活动已结束
```

演示时强调三点：

1. `userId` 不是前端传的，是从 token 里取的，改 query 参数无效；
2. 下单返回的是“处理中”临时订单，真正落库在 MQ 消费端；
3. 重复下单和活动时间都被拦住，不是只靠前端。

## 三、架构 60 秒讲法

```
请求 → JWT 拦截器 → 限流 → 商品/时间校验(MySQL)
     → SETNX 防重(Redis) → Lua 预扣库存(Redis)
     → 写事务表(MySQL) → 发 MQ
     → 消费者幂等校验 → 乐观锁扣 DB 库存 → 建订单 → 更新事务表
失败：重试队列(5s×3) → 死信队列；定时任务扫失败事务回补 Redis 库存
```

一句话：**Redis 挡流量，MySQL 保正确，MQ 削峰值，事务表兜可靠性。**

## 四、高频追问（按面试官思路排序）

### 1. 为什么用 Redis 预扣，不直接扣数据库？

秒杀的特点是“瞬时读多写少、库存极少”。直接打 DB 会有两个问题：一是行锁竞争把连接池打满；二是大量请求做无用功。
Redis 单线程 + Lua 把“查库存、判断、扣减”做成原子操作，能在内存里快速挡掉 99% 的无效请求，DB 只处理真正扣减成功的少量订单。

### 2. Lua 到底解决了什么？为什么不用 WATCH/MULTI？

如果先 `GET stock` 再 `DECR`，两条命令之间可能被其他请求插入，出现“都读到 1、都去扣”的竞态。
Lua 在 Redis 里是单线程原子执行的，脚本内 `get → 判断 → decrby → 不足则 incrby 回滚` 不会被打断。
`WATCH/MULTI` 是乐观事务，冲突要重试，高并发下重试率很高；Lua 更直接。

### 3. Redis 扣成功了，但 DB 扣失败怎么办？

这正是要“预扣 + 最终一致”的原因：Redis 只是预占名额，最终以 DB 为准。
消费端用 `UPDATE ... WHERE id=? AND version=? AND stock_count>0` 扣 DB；失败会重试，重试仍失败进死信队列，事务表标记失败，定时任务把 Redis 库存加回去。
代价是短暂不一致（Redis 已扣、DB 未扣），所以查询结果以下单后的订单/事务状态为准。

### 4. 怎么保证不超卖？说清楚三层。

1. Redis Lua：原子判断 + 扣减，库存不会扣成负数；
2. MySQL 乐观锁：`stock_count > 0 AND version = ?`，即使 Redis 与 DB 不一致，DB 也不会超卖；
3. 订单表唯一索引 `uk_user_goods(user_id, goods_id)`：兜底重复建单。

### 5. 有了 Lua 为什么还要 version 乐观锁？

Lua 管的是 Redis 里的“名额”，DB 是最终账本。两者可能因为重启、消息重试、人工修数而不一致。
`version` 保证并发更新时只有一个事务成功，失败方重试或走补偿，不会出现“两个线程都读到 10、都减成 9”。

### 6. 重复下单怎么防？为什么 TTL 不是几秒？

`SETNX seckill:user:{userId}:{goodsId}`，key 的 TTL 设置为“活动结束时间 + 60 秒”，覆盖整个活动周期。
早期版本写死 5 秒，5 秒后同一用户能再抢一单，和“一人一单”矛盾——这是我在压测时发现并修掉的。

### 7. MQ 消息重复消费怎么办？

消费前查 `transaction_log`：只有状态不是“成功(1)”且记录存在才继续；成功或记录不存在直接 ACK 跳过。
另外订单表有唯一索引，即使并发重复也只会成功一条。

### 8. 消息丢了怎么办？

- 下单前先写 `transaction_log(status=0)`，再发 MQ；
- 消费成功改 1，失败改 2；
- `TransactionCheckJob` 每 5 分钟扫 `status=2` 且超过 1 分钟的记录，回补 Redis 库存。

**要主动说缺口**：当前“发 MQ 失败”没有本地消息表重投，极端情况下事务会停在 0，需要人工/定时补偿。生产化会补 outbox + 定时重投。

### 9. 消费失败状态为什么曾经落不了库？

`createOrder` 带 `@Transactional`，原来在 catch 里写 `status=2` 再抛异常，事务回滚把失败标记也回滚了，状态永远是 0。
后来把失败标记拆成 `markTransactionFailed`，用 `REQUIRES_NEW` 独立事务提交。

### 10. 死信队列怎么设计的？

主队列声明 `x-dead-letter-exchange`；消费失败 `nack(requeue=false)` → 进重试队列（TTL 5 秒）→ 到期回主队列；重试 3 次仍失败 → 进 `seckill.order.dlq` 隔离。
重试次数从消息的 `x-death` 头统计，不依赖内存计数。
**边界**：死信只隔离，没有自动重放页面；重试间隔固定 5 秒，没有指数退避。

### 11. 对账任务会不会重复回补？

会存在“回补后原消息又被重试成功”的理论窗口。当前用“失败超过 1 分钟才回补”降低概率，但没有做严格幂等。
生产化应该给回补动作也加事务表和唯一约束。

### 12. 为什么用 MQ？不用行不行？

不用 MQ 就是同步建单：DB 写入成为瓶颈，接口 RT 直接受 DB 影响。
用 MQ 后接口只做 Redis + 事务表 + 发送，建单异步，能扛住瞬时峰值；代价是最终一致和消费可靠性要额外设计。

### 13. prefetch=1 + 手动 ACK 的取舍？

prefetch=1 保证单消费者一次只处理一条，失败影响面小，但吞吐受限；手动 ACK 保证“处理成功才确认”，避免消息丢。
生产可以适当调大 prefetch + 并发消费者，但要配合幂等。

### 14. JWT 为什么适合这里？注销怎么办？

JWT 无状态，服务端不用存 session，适合水平扩展。
当前没有 refresh token 和黑名单，注销只能等过期；生产化会加短期 access token + refresh token，或用 Redis 存 jti 黑名单。

### 15. 为什么 `userId` 不能由前端传？

前端传 `userId` 等于允许替别人下单。现在登录时把 `userId` 写进 token claim，拦截器验签后注入请求属性，Controller 用 `@RequestAttribute` 取，query 里的 `userId` 直接忽略。

### 16. 限流为什么用 Guava？分布式怎么办？

Guava `RateLimiter` 是单机令牌桶，实现简单、无额外依赖，适合单实例。
多实例下每个节点各自限流，总量会翻倍；生产要用 Redis + Lua 做分布式令牌桶，或网关/Sentinel 统一限流。

### 17. 为什么每次请求还查一次商品表？瓶颈在哪？

活动时间、商品存在性必须校验，走的是主键查询，成本可控；库存扣减仍然只走 Redis。
压测显示瓶颈主要在“事务表写入 + MQ 发布 + DB 连接池争用”，不是 Redis。生产化可以把活动信息缓存到 Redis，进一步减少 DB 查询。

### 18. 343 TPS 是怎么测的？为什么不是 README 原来写的 800？

`benchmark/LoadTest.java`，200 并发、持续 15 秒、库存调大、限流临时放开，本机单实例实测约 343 TPS，P95 707ms。
README 原来的 800 是模板数字，无法复现，我已经删掉换成实测值。机器是 i5-13500HX / 15.7G，MySQL/Redis/MQ 和应用同机，不能当生产指标。

### 19. 怎么证明零超卖？

500 库存、50 并发、4318 个请求，压测后查库：`stock_count=0`、订单 500、`transaction_log status=1` 500 条、Redis 库存 0。
SQL 和步骤都写在 `benchmark/README.md`，面试官可以现场复现。

### 20. Redis 挂了会怎样？

下单直接失败（Lua 执行异常），接口 500；DB 不会超卖，因为 DB 还有乐观锁。
生产化要做降级：本地缓存/限流兜底、Redis 集群、故障时快速失败而不是拖垮 Tomcat。

### 21. MySQL 挂了会怎样？

下单在“商品校验”阶段就失败；已经进 MQ 的消息会重试 3 次后进死信队列，事务表标记失败。
恢复后对账任务会回补 Redis 库存；但消息不会自动重放，需要人工处理死信。

### 22. 应用重启库存会被覆盖吗？

会。`initStockToRedis()` 每次启动按 DB 当前库存重置 Redis。重启前要清空队列，否则旧消息会继续建单。
这是已知问题，修法是 `setIfAbsent` 或按“DB 库存 - 已售”推导。

### 23. 为什么不用 Seata / RocketMQ？

Seata 偏强一致分布式事务，重、要额外部署，秒杀这种场景更适合“预扣 + 最终一致”。
RocketMQ 有事务消息、延迟消息，确实更合适；这里用 RabbitMQ 是为了练手 TTL + DLX 自己搭重试/死信，成本低、可控。

### 24. 如果做生产化，优先改什么？

1. 本地消息表/outbox，解决“发 MQ 失败”；
2. 活动信息缓存 + 多级限流；
3. 死信重放工具 + 指数退避；
4. 多实例下的分布式限流、分布式锁/分段库存；
5. 监控：TPS、RT、队列积压、死信数、对账差异告警。

### 25. 数据是你自己造的吗？会不会很假？

演示数据在 `sql/seckill.sql`，12 个商品、3 个账号，时间用 `NOW()` 相对生成，刻意构造了进行中/未开始/已结束三种状态，方便复现。
真实系统里商品由商品服务写入、用户来自统一认证；这个项目重点是验证并发方案和可复现的压测，不伪装成生产流量。

### 26. 这个项目你遇到的最大坑？

队列里残留的旧消息：清库后消费者还在消费“孤儿消息”，凭 Redis 库存继续建单，出现“订单数对不上”。
排查后发现是“只清了数据库，没清 MQ”，后来补了三件事：压测前 purge 三个队列、消费端事务幂等校验、失败消息不再无限 requeue。
